# Day 11: Recipes for Autotools and CMake Projects

This is the day most directly relevant to your existing work — your C++ `mqtt_monitor` capstone almost certainly already builds with CMake, and this is how you package it for real. Where Day 10 was manual `do_compile`/`do_install`, this day is "let the class do the work, and only override what's genuinely project-specific."

## CMake recipes — the common case for your codebase

```bitbake
SUMMARY = "MQTT device monitor service (C++)"
DESCRIPTION = "Multi-threaded serial ingestion, SQLite persistence, and MQTT publishing service"
HOMEPAGE = "https://github.com/georgeco/mqtt-monitor-cpp"
LICENSE = "MIT"
LIC_FILES_CHKSUM = "file://LICENSE;md5=<actual-hash>"

SRC_URI = "git://github.com/georgeco/mqtt-monitor-cpp.git;protocol=https;branch=main"
SRCREV = "abcdef123456..."
S = "${WORKDIR}/git"

DEPENDS = "mosquitto sqlite3 boost"

inherit cmake pkgconfig systemd

EXTRA_OECMAKE = " \
    -DCMAKE_BUILD_TYPE=Release \
    -DBUILD_TESTS=OFF \
    "

SYSTEMD_SERVICE:${PN} = "mqtt-monitor.service"
SYSTEMD_AUTO_ENABLE:${PN} = "enable"

FILES:${PN} += "${systemd_unitdir}/system/mqtt-monitor.service"
```

What `inherit cmake` actually gives you for free:

- `do_configure`: runs `cmake` with the correct cross-compilation toolchain file automatically generated by BitBake (`OEToolchainConfig.cmake` under the hood) — this is the part that would be genuinely painful to replicate manually, since it has to inject the right `CMAKE_SYSTEM_NAME`, `CMAKE_C_COMPILER`, sysroot paths, etc.
- `do_compile`: runs the generated build system (Ninja or Make, depending on `OECMAKE_GENERATOR`) with correct parallelism
- `do_install`: runs `cmake --install` (or `make install` depending on generator) targeting `${D}`

You almost never touch `do_configure`/`do_compile`/`do_install` at all with `inherit cmake` — your entire job is: set `DEPENDS` correctly, pass any CMake options your project needs via `EXTRA_OECMAKE`, and handle anything genuinely custom in `do_install:append()`.

## `EXTRA_OECMAKE` — passing your project's actual CMake options

If your CMakeLists.txt has options like:

```cmake
option(BUILD_TESTS "Build unit tests" ON)
option(ENABLE_MQTT_TLS "Enable TLS support" ON)
find_package(Boost REQUIRED COMPONENTS system thread)
```

Your recipe controls these the same way you'd pass them on a normal `cmake -D...` command line:

```bitbake
EXTRA_OECMAKE = " \
    -DBUILD_TESTS=OFF \
    -DENABLE_MQTT_TLS=ON \
    "
```

`BUILD_TESTS=OFF` is a real, common pattern — you don't want your GoogleTest suite (which you already use per your C++ curriculum) building and linking into a production recipe by default; that's DEPENDS you don't want to force on every consumer of this recipe unless explicitly testing. If you _do_ want to run your test suite as part of the Yocto build (legitimate for CI), that's `do_compile:append()` + `ptest` integration — a distinct, more involved topic (test recipes / `ptest` framework) worth flagging as existing but out of scope for a first pass; mention if you want it covered as an added day later.

## Autotools recipes — the other common upstream pattern

Many upstream C/C++ libraries (and `mosquitto` itself, depending on version) use autotools (`./configure && make && make install`):

```bitbake
SUMMARY = "Example autotools-based dependency"
LICENSE = "BSD-3-Clause"
LIC_FILES_CHKSUM = "file://COPYING;md5=..."

SRC_URI = "https://example.org/releases/libfoo-1.4.2.tar.gz"
SRC_URI[sha256sum] = "a1b2c3...actual-hash-here"

inherit autotools pkgconfig

EXTRA_OECONF = " \
    --disable-static \
    --enable-shared \
    --without-docs \
    "

PACKAGECONFIG ??= "ssl"
PACKAGECONFIG[ssl] = "--with-ssl,--without-ssl,openssl"
PACKAGECONFIG[tls-psk] = "--enable-tls-psk,--disable-tls-psk,"
```

`inherit autotools` gives you `do_configure` (runs `./configure` with correct cross flags — including regenerating `configure` via `autoreconf` if needed, handling the common "shipped configure script assumes host==target" problem automatically), `do_compile` (`make`), `do_install` (`make install DESTDIR=${D}`).

**`SRC_URI[sha256sum]`** — for non-git fetches (plain tarball URLs), you pin integrity via a checksum instead of `SRCREV`. BitBake refuses to proceed if the downloaded file's hash doesn't match — this is your protection against a compromised or altered upstream release, not just a formality. Get the correct hash from the upstream release page/checksums file, never fabricate one to make a build pass — that defeats the entire point.

## `PACKAGECONFIG` — the mechanism for optional build-time features

This deserves real attention since it's one of the more powerful and initially-confusing patterns in the ecosystem, and you'll definitely touch it configuring `mosquitto` (TLS support, bridge support) for your MQTT stack.

```bitbake
PACKAGECONFIG ??= "ssl"
PACKAGECONFIG[ssl] = "--with-ssl,--without-ssl,openssl"
```

Reading the format: `PACKAGECONFIG[<feature-name>] = "<configure-flag-if-enabled>,<configure-flag-if-disabled>,<extra-DEPENDS-if-enabled>,<extra-RDEPENDS-if-enabled>"`

- `PACKAGECONFIG ??= "ssl"` — sets the _default_ enabled feature set (weak default assignment — `??=` means "only if nothing else already set this," letting downstream layers/`local.conf` override without conflict).
- `PACKAGECONFIG[ssl] = "--with-ssl,--without-ssl,openssl"` — if `ssl` is in the enabled set: pass `--with-ssl` to configure, and add `openssl` to `DEPENDS`. If not enabled: pass `--without-ssl` instead, no extra dependency.

This means **you toggle optional features from `local.conf` or your own layer without ever touching the upstream recipe**:

```bitbake
PACKAGECONFIG:append:pn-mosquitto = " tls-psk"
```

(The `pn-mosquitto` override targets a specific recipe by name — useful when tweaking behavior for one specific dependency from your own layer/config, rather than editing that recipe's file directly.)

This is genuinely one of the best mechanisms in the whole system for staying out of upstream/community recipes while still controlling exactly which optional features get built — check any real recipe's `PACKAGECONFIG` lines before assuming you need a `.bbappend` to change build-time feature toggles; often you don't.

## Real example: configuring `mosquitto` for your stack via `PACKAGECONFIG`, not a fork

Instead of forking/patching the `meta-openembedded` mosquitto recipe, in your own layer's `.bbappend`:

```bitbake
# meta-mqtt-monitor/recipes-connectivity/mosquitto/mosquitto_%.bbappend

PACKAGECONFIG:append = " websockets"
```

Check first whether the upstream recipe even exposes the toggle you want:

```bash
bitbake-layers show-recipes mosquitto
bitbake -e mosquitto | grep ^PACKAGECONFIG
```

If `websockets` (or whatever feature) isn't a defined `PACKAGECONFIG` option in the upstream recipe at all, you can't toggle it this way — that's when a `.bbappend` adding your _own_ `PACKAGECONFIG[websockets]` entry (or a genuine patch) becomes necessary. Always check `bitbake -e` first before assuming you need to write more than a one-line append.

## CMake + `PACKAGECONFIG` together (your actual mqtt-monitor-cpp case)

```bitbake
inherit cmake systemd

PACKAGECONFIG ??= "tls"
PACKAGECONFIG[tls] = "-DENABLE_MQTT_TLS=ON,-DENABLE_MQTT_TLS=OFF,openssl"
PACKAGECONFIG[tests] = "-DBUILD_TESTS=ON,-DBUILD_TESTS=OFF,gtest"
```

Same mechanism as autotools, just with CMake-flavored flag syntax instead of `--with-x`/`--without-x` — `PACKAGECONFIG` is generic across build systems, since the flags are just opaque strings substituted into whatever the underlying class actually invokes.

## Debugging CMake-specific configure failures

```bash
bitbake mqtt-monitor -c devshell
cd ${B}   # note: B, not S — cmake's out-of-tree build directory
cmake ${S} -DCMAKE_TOOLCHAIN_FILE=$OECMAKE_TOOLCHAIN ... # replicate manually if needed
```

Or more directly, check the actual invocation BitBake used:

```bash
cat tmp/work/<arch>/mqtt-monitor/*/temp/log.do_configure
```

The full `cmake` command line BitBake ran is logged near the top — copy it, run manually inside `devshell`, iterate faster than full `bitbake` invocations while chasing a configure-time issue (missing `find_package`, wrong toolchain variable, etc.).

## Key takeaways

- `inherit cmake` / `inherit autotools` give you correct cross-compilation `do_configure`/`do_compile`/`do_install` for free — your job narrows to `DEPENDS`, `EXTRA_OECMAKE`/`EXTRA_OECONF`, and genuinely custom `do_install:append()` logic.
- `SRC_URI[sha256sum]` is the tarball-fetch equivalent of `SRCREV` for git — never fabricate a hash to force a build past a checksum mismatch.
- `PACKAGECONFIG` is the standard mechanism for toggling optional build-time features (and their associated `DEPENDS`/`RDEPENDS`) without forking recipes — check `bitbake -e <recipe> | grep PACKAGECONFIG` before assuming you need a patch.
- `${B}` (build dir) vs `${S}` (source dir) matters specifically for CMake's out-of-tree builds — `devshell` for CMake recipes puts you in `${B}` by convention.
- This is directly your production path for the C++ `mqtt_monitor` capstone — CMake options you already use (`BUILD_TESTS`, TLS toggles) map straight onto `EXTRA_OECMAKE`/`PACKAGECONFIG`.
